# TFA 工作清单：开发注意事项

> 配套《TFA 工作清单：需求文档》v1。本文只写「容易做错、做漏、做过头」的细节，按编号引用（如 `D-03`）。需求文档说**做什么**，本文说**怎么做才不坏**。
> 开发前通读一遍；每做完一期，对照本文过一遍清单。

---

## A. 总的边界（先记住这五条）

| # | 注意 |
| --- | --- |
| A-01 | **现有机制一行不删。** 工单、角色、规则、候选、定时、副作用队列、对账、`tfa` 现有命令、工单条、执行终端行为全部保留。新东西是「上面加一层任务」，不是替换。第 1 期的 diff 应该几乎只有新增文件和少量加字段。 |
| A-02 | **单一写入者。** 任务、清单项、工作流只经 `SuperagentEngine` 写 `superagent.db`；界面、CLI、运行时都不直接 SQL。CLI 写完发 Darwin 通知让 App 立刻 `pass()`（现有做法）。 |
| A-03 | **人能看到的概念只有五个**：任务、清单项、谁来做、工作流、需要你。工单、角色、规则、候选、决定在第二层（任务卡里、设置里）。界面上任何地方出现「Worker」「Router」「Trigger」都是错的。 |
| A-04 | **琥珀只表示需要你。** 阶段、优先级、执行者、进度都不着色。一屏里琥珀出现几处，人就有几件事要做。 |
| A-05 | **概念少、设置少。** 本文和需求文档没写的开关，默认不做。想加设置先问：「哪个团队会改它」；答不上来就用一个默认值。 |

## B. 数据与迁移

| # | 注意 |
| --- | --- |
| B-01 | `superagent.db` 加 `PRAGMA user_version` 并自增；迁移幂等（`kv.migrated.tasks = 1` 后不再跑）；迁移整体在一个 `BEGIN IMMEDIATE` 事务里；**跑之前先复制一份** `superagent.db.bak-<yyyyMMdd-HHmm>`（连同 `-wal`/`-shm` checkpoint 后再复制）。 |
| B-02 | 迁移只读工单生成任务，**不改工单的任何已有列**；`ticket.task_id` 回指。可重跑：已有 `task_id` 的工单跳过。 |
| B-03 | `ticket.task_id` 允许为空（旧工单、测试工单）。所有读任务的代码要容忍「没有任务的工单」，按旧行为显示在工单条和主管面板里，不崩、不隐藏。 |
| B-04 | 工作流模板**快照进任务**：`task.workflow_snapshot`（JSON）在建任务时复制模板，之后改模板不影响已有任务。`task.workflow` 只记模板 id 供显示。否则改一个阶段名，所有任务的 `stage` 都对不上。 |
| B-05 | `task.stage` 存阶段名，但代码判断只看快照里该阶段的 `kind`；找不到对应阶段（数据损坏）→ 当作 `doing` 的第一个阶段并记一条 timeline，不抛错。 |
| B-06 | 清单项 `ord` 从 1 开始、连续；增删项在同一事务里重排；**对外（CLI、请求文本、界面）永远显示 `ord`，不显示 `item.id`**。执行者说的「第 3 项」就是 `ord = 3`。 |
| B-07 | 有工单的清单项不能删、不能改 `assignee`（先取消工单）；文字可改，改了要 `tfa` 提示给执行者（走现有 `insertInput(.system)`）。 |
| B-08 | 任务不硬删。取消 = `status = cancelled`；界面的「删除」就是取消 + 从列表隐藏。工单同理（现有）。 |
| B-09 | 编号解析：CLI 接受 `A-12`、`a12`、`12`（同现有 `parseTicketID` 对 `#12` 的宽松解析）。错误提示写「任务 A-12 不存在」，不要暴露内部 id。 |
| B-10 | 打扰计数 `kv.interruption.<yyyy-MM-dd>` 用**本地日历日**（`Calendar.current`），不是 UTC；跨天在第一次写入时自然新建键，不做定时清零。 |
| B-11 | 索引：`item(task_id, ord)`、`ticket(task_id)`、`task(status, stage)`、`timeline(task_id, at)`。清单页每轮 Pass 只做一次聚合查询，不要 N+1。 |
| B-12 | `task.request` 原样存，不 trim 内部换行；上限与工单一致。`title` ≤80 字、`item.text` ≤200 字，超了报错不截断（人写的）；主管生成的超长就截断并记 timeline。 |

## C. 引擎与事务

| # | 注意 |
| --- | --- |
| C-01 | `assign(... .agent(role))` 必须复用现有建工单的路径（`createTicket` 加 `taskID / itemIDs` 参数），让 Mandate、Assignment、`launch` effect、槽位、worktree 逻辑一个不漏。**不要写第二套建工单代码。** |
| C-02 | 同一任务里、同一角色、同一次分配，`oneTicket = true` 合成一张；不同角色各一张；不同任务永远不合并。工单 `item_ids` 只能指向自己任务的项（引擎断言）。 |
| C-03 | 重分配：Agent → 你，要先 `stop` 那张工单（界面弹确认，列出会被中断的终端）；你 → Agent，直接建工单；Agent(助理) → Agent(开发)，先停再建，timeline 记「改派」。 |
| C-04 | 每次清单项状态变化后，在**同一事务**里调 `advanceIfComplete`；只前进一个阶段；到 `done` 停。进入 `review` 入队 `notify`；进入 `done` 写 `resultSummary`（有工单取最后一张 ready 的 summary，否则留空由人填）。 |
| C-05 | 任务在 `review` 时新增清单项 → 回到 `doing`（记 timeline「新增第 n 项，回到进行中」）；在 `done` 时新增 → 重新打开（`status = open`，回 `doing`）。 |
| C-06 | `needsYou` 是**派生值**（视图里算），不存库；但任务要有 `notified_stage` 列做通知去重（同工单的 `notifiedStage` 一样的逻辑）。 |
| C-07 | 回报映射见需求文档 §5.3；额外边界：工单回报时它的某个清单项已被人改派或取消 → 忽略那一项，记 timeline，不报错给执行者（执行者改不了这事）。 |
| C-08 | `handback` → 新任务（`source = handback`，`source_ref = "#<工单>"`，scope 同原任务，一项 = 退回的请求），原清单项回 `todo / unassigned`。不要把退回的请求挂回原工单（原型和现有 prompt 都禁止）。 |
| C-09 | `cancelTask` 对名下打开的工单调现有 `stop(by: "你")`；常驻角色正在做别的单时不中断（现有规则）。 |
| C-10 | 对已完成任务的任何跟进（打回、补充、新增项）→ `reopen`（同工单的 `reopen`），`status = open`、`stage = 第一个 doing`。被取消的任务不能重开（同「已停止的工单不能挂接」）。 |
| C-11 | 「你」的清单项**永远不占** WorkerSlots，`busyCount` 不变；不建 Assignment，不建终端。 |
| C-12 | `now()` 继续可注入；事务里不做 I/O、不等终端；副作用一律入队。 |
| C-13 | 自动推进阶段时如果下一阶段是 `review` 且 `owner` 是你自己（个人层恒成立）：仍然进 review 并进「需要你」——这是「按影响停」的点，不要为了省一步自动通过。 |
| C-14 | 依赖：前置任务未 `done` 时，`assign` 到 Agent 要拒绝（「A-11 还没完成」）；分配给你允许（人自己判断）。前置任务被取消 → 依赖它的任务的清单项标 `blocked`，进「需要你」。 |

## D. 回报与执行者侧的边界

| # | 注意 |
| --- | --- |
| D-01 | `tfa report --item n`：`n` 是任务里的 `ord`；不在这张工单 `item_ids` 里 → 报错「第 n 项不归这张工单（你负责的是 3、4）」。常驻角色终端必须同时给 `--ticket`。 |
| D-02 | `ready` 把这张工单的所有项标 done（包括执行者忘了 `--item` 的）；`progress --item` 只是锦上添花，**不要**在 prompt 里要求必须逐项报，否则 Agent 会为了合规多说话。 |
| D-03 | `blocked / --ask / failed` 把该工单的项标 `blocked`；人回答（现有 `feedback`，清空 `attention`）后项回到 `doing`。 |
| D-04 | `dropped`：项回未分配；任务不自动取消。只有当任务的所有项都未分配且没有一项 done，界面才出现「已放弃？」确认按钮；人点了才 `dropped`。 |
| D-05 | `waiting`（停下未报）由 TFA 自己记，不改清单项；只进 `needsYou.stalled`。 |
| D-06 | 执行者看到的请求文本（需求文档 §5.2）里「其余清单项」只列序号和一句话，**不写谁在做、不写别人的工单号**——执行者不该去碰别人的项。 |
| D-07 | 送达规则不变：请求文本 >1500 字时开场只打一行「[TFA #12] 任务 A-12「标题」，`tfa read ticket 12` 读全部」。清单项多时很容易超，按长度判断，不按项数。 |
| D-08 | 工单的 `role.edits == false`（助理）时，清单项文字含「改 / 修 / 提交 / 实现」的，分配界面给一句提示「这项看起来要改文件，助理只读」，但不拦（人决定）。 |

## E. CLI 与 prompt

| # | 注意 |
| --- | --- |
| E-01 | 主管终端的放行是 `Bash(tfa:*)`，所以**任何新的 `tfa` 子命令主管都能跑**。权限要在引擎里按调用方判断：主管终端启动时加环境变量 `TFA_ROLE=router`；`task assign / done / approve / reject / cancel` 在 `TFA_ROLE=router` 下一律拒绝，提示「谁来做由人在清单里决定」。执行者终端（有 `TFA_TICKET` / `TFA_AGENT`）同样拒绝这些命令和 `task add`（要新任务用 `handback`）。 |
| E-02 | `tfa task add --suggest 3=助理,4=开发`：角色名必须在 `tfa read roles` 里，否则报错并列出可选角色。建议只是默认值，**不建工单**；测试里专门断言「主管 add 之后工单数不变」。 |
| E-03 | `--item` 可重复；多行场景支持 `--items -` 从 stdin 一行一项（沿用 heredoc 约定：含换行或引号时省略参数从 stdin 读）。 |
| E-04 | `tfa task show` 的清单项编号、执行者请求文本里的编号、界面上的编号必须同源（`ord`）。写一个共用的格式化函数，三处都调它。 |
| E-05 | `tfa read`（总览）加一段「任务（需要你 N / 进行中 M / 待分配 K）」放在最前；工单列表保留给主管问进度时用。 |
| E-06 | 主管 prompt 只改「人的消息」一节（需求文档 §8），其余一字不动；改完跑一遍现有的 prompt 相关测试。新规则措辞：「新的工作请求用 `tfa task add` 加进人的清单并给出清单项与角色建议；不要 `route accept`，除非人明确说直接让 Agent 做」。 |
| E-07 | 执行者 prompt 加的两句放在「开始」和「回报」节末尾；不要改「只在这些情况停下问人」那段——那是行为的核心。 |
| E-08 | `Prompts.install` 内容没变不写文件（现有）；改了 prompt 要在 CHANGELOG 里写一句，常驻角色的终端重启后才生效，说明给人看。 |
| E-09 | CLI 输出继续短中文、无歧义、给 LLM 读；错误码：参数错 2、业务错 1（现有）。新命令的 `help` 文本同步更新。 |

| # | 注意 |

| F-04 | 清单页在 760pt 列里；分区 `需要你 / 进行中 / 待分配 / 已完成`，空分区不显示（「健康状态不占空间」），全空显示空状态：「清单是空的。对主管说一句，或点 +。」 |
| F-05 | 清单行高 48：第一行 `A-12` 等宽 + 标题（`rowTitle`，截断，tooltip 全文）+ 右侧阶段 `StateTag`；第二行 `rowSubtitle`：进度 `3/5`（`.monospacedDigit()`）· 执行者 chips（你 / 开发 / 助理，去重，最多 3 个）· 截止（只在 3 天内显示）。右端一个动作按钮（需要你：该阶段的动作；待分配：「谁来做…」；其余无）。 |
| F-06 | 行点击 = 打开任务卡（同一面板内推入，带返回）；不要用 sheet 开任务卡，人会在卡里停留很久。 |
| F-07 | 任务卡最大宽 760，可滚动；顺序固定：头卡（标题 → 阶段步进 → 元信息一行文字，只有可点的保留 chip）→ 需要你条 → 清单 → 活动 → 同步行 → 底部动作（只剩取消任务…）。缺的部分不占位（活动为空不渲染）。（2026-11-08 设计评审 6A 改：需要你条提到清单之前，阶段条并入头卡。） |
| F-08 | 阶段步进：头卡内标题下一行 24px 文字「待领取 › 进行中 › 待评审 › 完成」；当前段 charcoal 半粗 + 2px charcoal 下划线，已过段石灰，未到段浅石灰；**不用颜色区分阶段**。它是状态，所以是卡上最轻的墨，最重的给需要你条。（2026-11-08 设计评审 6A 替换了原来 32px 填充条。） |
| F-09 | 清单项行 40px：勾选框 24px（你的项可点；Agent 的项只读，用 `◐` 表示工作中、`✓` 完成、`○` 待做、`⊘` 受阻），文字可换行到两行，右侧执行者 chip（你 = cream + 墨色描边；角色 = cream）、工单号 chip（等宽，可点跳终端）、状态词。 |
| F-10 | 需要你条：44px，琥珀 6% 底 + 琥珀描边，左侧方块标记，一句话（问题原文或阶段说明），右侧该阶段的 1–2 个动作：回答… / 打回… + 完成任务…（先弹确认单列出要合并的分支）/ 补充…（主）+ 重试（次）/ 失败才以重试为主；退回的项写「工单 #13 退回了一件事 → 已成为任务 A-13，等你定谁来做」+ 去分配 A-13…；待评审加「看改动」。正文固定前缀「工单 #12 回报：」。一张卡只有一条；多件事按 `PersonAction` 顺序取第一件，其余写成一行小字「还有 1 件：…」。 |
| F-11 | 执行终端的工单条加一个 chip「任务 A-12」，点了打开任务卡；任务卡里的工单号点了跳终端（`activateTerminal`）。两边互跳是「订阅扇出」的界面形态。 |
| F-12 | 「谁来做」sheet 宽 560：每项一行——序号、文字（可编辑）、分段控件（你 / 各角色，按 `tfa read roles` 顺序）；底部「同一角色合成一张工单」开关（默认开）+ 一句说明「交给 Agent 的项会开工单；在哪个目录、能否改文件由角色决定」。⌘↩ 确认，Esc 取消；有改动未确认关闭时按 `DESIGN.md` 的保存 / 放弃 / 取消三选。 |
| F-13 | 默认执行者启发式只在没有主管建议时用：含「改 / 修 / 实现 / 提交 / 加 / 删」→ 开发；含「查 / 问 / 分析 / 总结 / 看看」→ 助理；其余 → 你。写成纯函数，单测。 |
| F-14 | 待处理中心（`Workspace.swift`）列**任务**而不是工单；一条任务一行；终端错误照旧。侧栏「待处理」角标 = 需要你的任务数 + 终端错误数，同一任务不重复计。 |
| F-15 | ⌘] / ⌘⇧]：先跳需要你的任务卡，再跳需要你的终端；跳到任务卡时面板打开并滚到需要你条。 |

## G. 通知与打扰

| # | 注意 |
| --- | --- |
| G-01 | 通知粒度是**任务 × 阶段**（`task.notified_stage`），不是工单；一张任务两张工单同时需要你 → 一条通知「任务 A-12 有 2 件事需要你」。 |

| G-04 | 关窗驻留菜单栏时通知照发（现有行为）；点通知打开任务卡而不是终端。 |

## H. 安全边界

| # | 注意 |
| --- | --- |
| H-01 | 主管终端继续 `--permission-mode dontAsk` + 只放行 `tfa`；新命令的「谁能调」在引擎里按 `TFA_ROLE / TFA_TICKET / TFA_AGENT` 判（E-01）。 |
| H-02 | 任务的 `scope` 目录在分配给 `edits == true` 的角色时校验：存在、是目录、不是家目录或根目录（现有工单目录规则）。分配给助理或你不校验。 |
