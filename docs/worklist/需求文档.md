# TFA 工作清单：需求文档（个人工作台 → 组织协作）

> 状态：待开发。版本：v1，2026-11-08。
> 配套图：设计画布里的三张图——《两张工作清单》（总流程）、《任务的一生 · 三条泳道》（状态与规则）、《一个任务长什么样》（任务卡解剖）。本文是那三张图的文字版，字段、命令、验收标准以本文为准。
> 读者：在 TFA 仓库里开发的 agent 与人。仓库约定见 `AGENTS.md`（中文沟通、`swift build` 为准、有 `Tests/` 就跑 `swift test`、不加 Co-Authored-By）。

## 0. 一句话

**TFA 从「主管 + 工单」改成「工作清单 + 谁来做」。** 人的工作单位是**任务**（有工作流和工作清单），不是工单；TFA 首屏是**我的清单**，不是主管终端；每个任务（或任务里的每个清单项）先由人决定**谁来做**——自己，还是交给某个角色的 Agent——交给 Agent 的那部分才变成工单，走现有的主管 / 执行者 / 回报机制。个人清单可以单独用，也可以注册到组织的服务端清单，领取组织派下来的任务并回传进度。

现有的 Super-agent 实现（`Sources/SuperagentCore`、`Sources/TFACLI*`、`Sources/Mux/Superagent*.swift`）**全部保留**，位置从「入口」退到「执行层」。

---

## 1. 为什么改

| 现状（v0.22 Unreleased） | 问题 | 改法 |
| --- | --- | --- |
| 入口是「主管」终端：人用自然语言提需求，主管直接 accept 成工单 | TFA 看起来是在「管 Agent」；人自己要做的事没地方放；一件事里一部分人做、一部分 Agent 做没法表达 | 入口改成**我的清单**；任务先进清单，再定谁来做 |
| 工单 = 终端 = worktree，一个请求一张 | 粒度是 Agent 的，不是人的 | 任务是人的单位，工单挂在任务的清单项下 |
| 「需要你」散在工单条、待处理、主管面板三处 | 人要到处找 | 需要你只出现在清单（琥珀标记）和任务卡上 |
| 单机、单人 | 团队没法用 | 同一套任务模型放到服务端，TFA 注册为节点，领取 / 派单 / 回传 |

原则不变（照搬 Super-agent 原型 `docs/000`）：**尽量少占用人的注意力，尽量多给价值。** 概念少、设置少、面板只列需要人的、一次只问一个问题。

## 3. 领域模型

```
Task ──1:n──▶ Item ──0:1──▶ Ticket（现有：Assignment / Report / Attention）
 │  ▲                │
 │  └── Workflow（阶段）└── 回报自动推进 Item.status
 │
 ├── source：manual | router | rule | schedule | handback | org
 ├── scope：目录（个人）/ 组织范围 id
 ├── deps：[Task.id]
 └── sync：local | synced | pending | conflict（第 3 期）
```

### 3.1 Task（任务）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Int64 | 本地自增；界面 `A-<id>` |
| `origin` / `originID` | String? | 来自组织时：组织工作区 + 组织任务号；本地任务为空 |
| `title` | String ≤80 | 标题 |
| `request` | String | 原文（人的话 / 事件原文）。执行者从这里推导需求，标题不能替代 |
| `source` | enum | `manual`（在清单里建）/ `router`（对主管说的）/ `rule`（候选自动接单）/ `schedule` / `handback`（Agent 退回）/ `org`（组织派来 / 领取） |
| `sourceRef` | String? | 群 / PR / Issue 链接，或触发它的 `t<id>` |
| `scope` | String | 个人：项目目录（可空 = 不针对项目）；组织：范围 id |
| `owner` | String | 负责人；个人层恒为「你」 |
| `due` | Double? | 截止 |
| `priority` | enum | 高 / 中 / 低（默认中） |
| `deps` | [Int64] | 前置任务；有未完成的前置时不可领取 / 不可开始 |
| `workflow` | String | 工作流模板 id；默认 `default` |
| `stage` | String | 当前阶段名 |
| `status` | enum | `open` / `done` / `cancelled` / `dropped` |
| `resultSummary` | String | 完成时的一句话结果（回到原处用） |
| `note` | String ≤30 词 | 路由备注（现有工单的 note 语义） |
| `createdAt` / `updatedAt` | Double | |
| `syncState` / `syncedAt` | | 第 3 期 |

**派生，不存库**：`needsYou: [PersonAction]`（见 §4.3）、`progress: done/total`。

### 3.2 Workflow（工作流）

```json
{"id":"default","name":"默认","stages":[
  {"name":"待领取","kind":"todo"},
  {"name":"进行中","kind":"doing"},
  {"name":"待评审","kind":"review"},
  {"name":"完成","kind":"done"}]}
```

- `kind` 决定行为：`todo`（没人做）、`doing`（清单项在推进）、`review`（等负责人通过 / 打回）、`done`（终态）。一个模板恰好一个 `doing`、一个 `done`，`review` 可有可无，可有多个 `doing`（如「开发 → 测试」）。
- 个人层：内置 `default` 与 `no-review`（待领取 → 进行中 → 完成）；用户可在设置里新建模板并按项目目录指定默认。组织层按范围指定。
- 阶段名是显示用的；代码只看 `kind` 和顺序。

### 3.3 Item（清单项）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Int64 | |
| `taskID` | Int64 | |
| `ord` | Int | 顺序 |
| `text` | String ≤200 | 一句话，可验证的结果（「改为分段加锁并跑回归」），不是动作 |
| `assignee` | enum | `.unassigned` / `.you` / `.agent(role: String)` |
| `status` | enum | `todo` / `doing` / `done` / `blocked` |
| `ticketID` | Int64? | 交给 Agent 后挂的工单 |
| `doneAt` / `doneBy` | | 「你」或角色名 |

一张任务至少 1 个清单项（没写清单的任务，自动生成一项 = 标题）。

### 3.4 Ticket（工单，现有）增加

| 字段 | 说明 |
| --- | --- |
| `taskID` | 所属任务 |
| `itemIDs` | JSON 数组：这张工单负责哪些清单项 |

工单的 `request` 由任务生成（§5.2），`repo` = 任务的 `scope` 目录，`role` = 分配时选的角色。其余（Assignment、Report、Attention、Mandate、session、dir、branch）不变。

### 3.5 需要确认的建模取舍

- **一个清单项最多一张工单**；一张工单可以带几个清单项（同一角色、同一任务）。
- **任务不跟随工单的状态**：工单结束不等于任务完成；只有清单项全部 `done` 才推进阶段（原型的「Ticket 不跟随会话」同一思想）。
- **「你」做的清单项不产生任何副作用**：没有终端、没有工单，只是你手动勾。

## 4. 状态机（对应《任务的一生》）

### 4.1 任务阶段（组织清单与个人清单共用）

| 从 | 到 | 谁 / 什么推动 |
| --- | --- | --- |
| 候选（只观察，不是任务） | 待领取 | 范围负责人审阅「判断正确」；或接单模式为自动 |
| 待领取 | 进行中 | 人领取 · TFA 自动领取 · 负责人派单（个人层：建好即进行中，没有待领取） |
| 进行中 | 下一阶段 | 该阶段里所有清单项 `done`（自动） |
| 待评审 | 完成 | 负责人「通过」 |
| 待评审 | 进行中 | 负责人「打回」（附意见；意见作为新清单项或送给原工单，见 §5.4） |
| 进行中 | 待领取 | 转交给别人（第 3 期）；进度随任务走，工单不走 |
| 任一 | 已取消 | 负责人取消；正在跑的工单一并停止 |
| 任一 | 已放弃 | 所有 Agent 清单项都报 `dropped` 且人确认 |
| 完成 | — | `resultSummary` 回到原处（群 / PR 评论一句话，≤100 词）；进审计 |

### 4.2 清单项

| 从 | 到 | 推动 |
| --- | --- | --- |
| todo | doing | 「你」：手动；Agent：工单 `ack` |
| doing | done | 「你」：手动勾；Agent：工单 `report --state ready`（全部）或 `report --item n`（单项） |
| doing | blocked | Agent：`report --state blocked` / `--ask`；人回答后回到 doing |
| 任一 | todo（未分配） | Agent：`dropped` 或 `handback` 越界 → 清单项回到未分配，任务卡标「待重新分配」 |

### 4.3 需要你（派生）

任务的 `needsYou` = 它名下所有打开工单的 `PersonAction`（现有 `Stage.person`）∪ `{review}`（当前阶段 `kind == review` 且你是负责人）∪ `{blocked}`（清单项 blocked 且无工单，例如前置任务被取消）。排序沿用 `PersonAction` 的声明顺序：answer → review → blocked → failed → delivery → stalled。

**一次「需要你」= 一次打扰**：进入 `needsYou` 时发一次系统通知（沿用 `notify` effect，`notifiedStage` 去重），当天计数 +1。

## 5. 引擎规则（`SuperagentCore`）

单一写入者不变：所有领域数据只经 `SuperagentEngine` 写入 `superagent.db`；CLI 和界面都只提交命令。

### 5.1 新增命令（Engine 方法）

| 方法 | 做什么 |
| --- | --- |
| `createTask(title, request, source, sourceRef, scope, items:[String], workflow, priority, due, deps)` | 建任务；没有 items 就生成一项 = 标题；个人层直接进 `doing` 阶段（跳过 todo） |
| `updateTask(id, patch)` | 改标题 / 截止 / 优先级 / 依赖 / 范围 |
| `addItems(taskID, [text])` / `editItem` / `removeItem` | 改清单；已有工单的项不能删，只能取消工单后再删 |
| `assign(taskID, itemIDs, to: Assignee, oneTicket: Bool)` | **谁来做**。`to = .you`：清单项标为你的；`to = .agent(role)`：为这些项建工单（`oneTicket` 为真时合成一张），走现有 `accept` 逻辑（Mandate、Assignment、launch effect） |
| `itemDone(taskID, itemID, by)` | 人手动勾；或由 `report` 调用 |
| `advanceIfComplete(taskID)` | 当前阶段所有项 done → 进入下一阶段；进入 `review` 时入队 notify；进入 `done` 时写 `resultSummary`（取最后一张工单的 summary 或人填的） |
| `approveTask(taskID, by)` / `rejectTask(taskID, text, by)` | 通过 → 完成（有工单分支的，沿用现有合并逻辑：先合并再结）；打回 → 进行中，意见送给原工单（`feedback`）或新建清单项（没有工单时） |
| `cancelTask(taskID, by)` | 取消；名下打开的工单 `stop` |
| `transferTask(taskID, to person)` | 第 3 期 |

### 5.2 分配给 Agent 时生成的工单请求（`request`）

```
[任务 A-12] 结算对账任务偶发超时
原文：<task.request>
你负责的清单项：
3. 改为分段加锁，跑回归
4. 在支付研发群回复结论
其余清单项（不归你）：1 复现超时 ✓ · 2 定位根因 ✓ · 5 评审 PR（你）
目录：<task.scope>
完成一项就 `tfa report --state progress --item <n> --summary …`；全部完成报 ready。
```

路由备注 `note` 沿用任务的 `note`。工单标题 = 任务标题 + 清单项序号。

### 5.3 回报映射（扩展现有 `report`）

| 回报 | 对清单项 | 对任务 |
| --- | --- | --- |
| `ack` | 这张工单的所有项 → doing | — |
| `progress --item n` | 第 n 项 → done | `advanceIfComplete` |
| `ready` | 这张工单的所有项 → done | `advanceIfComplete`；不需评审的角色仍按现有逻辑自动结单 |
| `blocked` / `--ask` | 项 → blocked | `needsYou` 含 answer / blocked |
| `failed` | 项 → blocked | `needsYou` 含 failed |
| `dropped` | 项 → todo、未分配 | 任务卡标「待重新分配」；全部项都 dropped 且人确认 → 已放弃 |
| `handback` | 退回的请求成为**新任务**（source = handback，scope 同原任务），原清单项 → 未分配 | 新任务出现在「待分配」 |

### 5.4 候选、定时、主管的入口全部改成「进清单」

| 来源 | 现在 | 改后 |
| --- | --- | --- |
| 主管接到新工作 | `tfa route accept` 直接建工单 | `tfa task add`：建任务，附主管建议的清单项（2–5 条）和每项建议的角色；**不分配**。人说「直接让 Agent 做」才 `tfa task add --assign-all <角色>` |
| 追问 / 回答 / 打回 | `tfa route attach <工单>` | 不变（工单层）；主管可用 `tfa task show A-12` 找到工单号 |
| 候选研判通过（自动接单） | `eval decide --decision accept` 建工单 | 建任务 + 全部清单项分配给规则指定的角色（规则新增 `role` 字段，默认开发） |
| 候选研判通过（只观察） | 记 `would_accept` | 不变，进观察记录；范围负责人可标「判断正确 / 不该接」（第 2 期） |
| 定时任务 | 交给主管 accept | 建任务（source = schedule），按定时任务上配置的 `assignee` 自动分配或留待分配 |
| Agent 退回（handback） | 主管重新 accept / ignore | 新任务进「待分配」，主管只转告 |

### 5.5 并发与送达（不变）

WorkerSlots（默认 3，人的跟进 +1）、deliver / relay / notify / stop effects、对账（会话丢失重开、agent 退出、停下未报催一次）全部沿用。「你」做的清单项不占槽。

## 6. `tfa` 命令行

新增 `task` 子命令；现有命令不删。输出仍是短中文、给 LLM 读。

```
tfa task add --title T [--request 原文 | heredoc] [--scope DIR] [--item "…"]... [--suggest 3=助理,4=开发] [--assign-all 角色] [--priority 高|中|低] [--due YYYY-MM-DD] [--dep A-11]
tfa task list [--needs-you] [--scope DIR] [--stage S]
tfa task show A-12                      # 任务 + 清单 + 挂的工单 + 活动
tfa task assign A-12 --item 3,4 --to 开发|助理|你 [--one-ticket]
tfa task done A-12 --item 4             # 人手动勾（界面也调它）
tfa task approve A-12 | reject A-12 --reason "…" | cancel A-12
tfa report --state progress --item 4 --summary "…"   # 执行者勾单项（新 flag）
```

- 主管终端只放行 `tfa task add|list|show` 和现有路由命令；`assign / done / approve / cancel` 只给人（界面）和 `--to` 由人确认的场景。主管要分配必须经人：它只能 `--suggest`。
- 执行者终端：`tfa read ticket` 的输出里增加「所属任务」和「你负责的清单项」。

## 7. 存储（`superagent.db`，WAL）

```sql
CREATE TABLE task (id INTEGER PRIMARY KEY, origin TEXT, origin_id TEXT, title TEXT NOT NULL, request TEXT NOT NULL,
  source TEXT NOT NULL, source_ref TEXT, scope TEXT NOT NULL DEFAULT '', owner TEXT NOT NULL DEFAULT '你',
  due REAL, priority TEXT NOT NULL DEFAULT 'medium', workflow TEXT NOT NULL DEFAULT 'default', stage TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'open', result_summary TEXT NOT NULL DEFAULT '', note TEXT NOT NULL DEFAULT '',
  created_at REAL NOT NULL, updated_at REAL NOT NULL, sync_state TEXT NOT NULL DEFAULT 'local', synced_at REAL);
CREATE TABLE task_dep (task_id INTEGER NOT NULL, depends_on INTEGER NOT NULL, PRIMARY KEY (task_id, depends_on));
CREATE TABLE item (id INTEGER PRIMARY KEY, task_id INTEGER NOT NULL, ord INTEGER NOT NULL, text TEXT NOT NULL,
  assignee TEXT NOT NULL DEFAULT '', status TEXT NOT NULL DEFAULT 'todo', ticket_id INTEGER, done_at REAL, done_by TEXT);
CREATE TABLE workflow (id TEXT PRIMARY KEY, name TEXT NOT NULL, scope TEXT NOT NULL DEFAULT '', stages TEXT NOT NULL);  -- JSON
ALTER TABLE ticket ADD COLUMN task_id INTEGER;  ALTER TABLE ticket ADD COLUMN item_ids TEXT NOT NULL DEFAULT '[]';
ALTER TABLE timeline ADD COLUMN task_id INTEGER;   -- 活动按任务聚合
-- kv：interruption.<yyyy-mm-dd> = 当天打扰次数；settings.interruption_budget（默认 8）
```

**迁移**：现有每张打开的工单 → 一个任务（title / request / repo 原样，source 按 trigger.source 映射，workflow = 角色需要评审 ? default : no-review），一个清单项 = 标题，assignee = `.agent(ticket.role)`，`ticket_id` 回指；阶段按工单现状（待评审 → review，其余 → doing）。已结束的工单 → 已完成 / 已取消的任务（只做 30 条最近的，其余不迁）。

## 8. 主管与执行者的 prompt 变化（`Prompts.swift`）

**主管**（只改「人的消息」一节）：
- 新的工作请求 → `tfa task add`，`--item` 写 2–5 条可验证的结果，`--suggest` 给每项建议角色；回一句「已加入你的清单：A-12「标题」，去定谁来做」。不再直接 accept，除非人明确说「直接让 Agent 做」。
- 问进度 → `tfa task show`，按清单项回答。
- 其余（追问 attach、停止、候选研判、对人说话 ≤100 词）不变。

**执行者**（`worker(role:)`）：
- 「开始」一节加：`tfa read ticket` 里有所属任务和你负责的清单项；只做自己的项，别的项是别人的（人或别的 Agent）。
- 「回报」一节加：完成一项就 `report --state progress --item n`；全部完成再 `ready`。

## 9. 界面（`Sources/Mux`，遵守 `DESIGN.md`）

### 9.1 首屏：我的清单

- 侧栏顶部固定行「**我的清单**」（在「主管」行之上；`list.bullet.clipboard` 图标）：副标题「N 件需要你」（琥珀）/「N 件进行中」。点击在详情区打开清单。「主管」行保留，副标题改为「对我说一句就能加任务」。
- 清单页（替换 `SuperagentPanel` 的首屏；角色 / 规则 / 定时 / 设置 / 决定日志挪到页底「设置」折叠区）：
  - 分区顺序：**需要你**（只在非空时显示，琥珀计数）→ **进行中** → **待分配**（有未分配清单项的任务）→ **待领取**（组织，第 3 期）→ **已完成**（折叠，最近 30）。
  - 筛选：今天 / 本周 / 按项目（范围）；搜索框。
  - 每行：`A-12` · 标题 · 阶段标签（`StateTag`，只有需要你时着色）· 清单进度 `3/5` · 执行者 chips（你 / 开发 / 助理，去重）· 右侧一个动作（需要你：该阶段的动作；待分配：「谁来做…」）。
  - 顶部一行：「今天打扰你 N 次 / 预算 8 · 替你处理 M 项」（第 2 期）。
- 「+ 任务」：标题 + 原文（可选）+ 范围（项目目录）+ 清单项（每行一条）+ 工作流模板；建完直接弹「谁来做」。

### 9.2 任务卡（按《一个任务长什么样》）

头卡（标题行 → 阶段步进「待领取 › 进行中 › 待评审 › 完成」→ 元信息一行文字：来源 · 范围 · 负责人 · 截止 · 优先级，依赖 / 来源工单 / 组织编号保留可点的 chip）→ 需要你条（琥珀；该阶段的动作按钮：回答… / 打回… · 完成任务… / 补充… · 重试 / 去分配 A-13…）→ 工作清单（每项：勾选框 · 文字 · 执行者 chip · 工单号 · 状态；卡头放「谁来做…」「+ 加一项」）→ 活动（时间线，带编号；为空不渲染）→ 同步行（第 3 期）→ 底部动作：取消…。（2026-11-08 设计评审改：需要你条提到清单之前，阶段条并入头卡，见注意事项 F-07 / F-08。）

- 点工单号 → 跳到那个执行终端（现有 `activateTerminal`）；执行终端的工单条上加「任务 A-12」可跳回。
- 你的清单项：勾选框可点；Agent 的项：勾选框只读，由回报推进。

### 9.3 「谁来做」sheet

- 列出全部未分配（和已分配、可改）的清单项，每项一个分段控件：**你 / 助理 / 开发 / 评审 / …**（现有角色），默认取主管的 `--suggest`，没有就按启发式（文字含「改 / 修 / 实现 / 提交」→ 开发；含「查 / 问 / 分析 / 总结」→ 助理；其余 → 你）。
- 底部选项：「同一角色的项合成一张工单」（默认开）。
- 确认 → `assign`；交给 Agent 的项立刻出现工单号和「排队中」。
- 不在这里选机器、目录、交付方式——这些由范围规则和角色定义决定（现有 `Role.standing / edits / review`）。

### 9.4 需要你与通知

- 「待处理」中心（`Workspace.swift`）：列任务（不是工单），每行给该阶段的动作；终端错误照旧。
- 系统通知：每个任务每个阶段一次（沿用 `notifiedStage`）；文案「任务 A-12 等你回答：<问题>」。
- ⌘] 跳到下一个需要你的东西：优先任务卡（需要你）、其次终端。

### 9.5 设计系统映射

状态色只用 `Theme.Status` 三种：需要你 = amber；失败 / 送达失败 = brick；完成 = sage；工作中 = 墨色（等化器）；其余石灰。阶段条、清单项行、执行者 chip、需要你条是新组件，写进 `DESIGN.md §9`。无阴影、9.6 / 16 圆角、系统字体。

## 10. 组织端（第 3 期）

同一套任务模型放到服务端。TFA 是一个**节点**：注册后领取 / 接收派单、回传进度；不注册照常用。

### 10.1 服务端对象

| 对象 | 字段要点 |
| --- | --- |
| 工作区 Workspace | 一个组织一个；成员、管理员 |
| 范围 Scope | 群 / 仓库 / 项目；负责人；允许发起的人；工作流模板；接单模式与规则（版本化，沿用 `Policy`）；打扰预算 |
| 任务 Task | 与 §3.1 同构，多 `assigneeNode`（领走它的节点）、`assigneePerson`、`claimedAt` |
| 节点 Node | 节点 id、人、在线、负载（打开工单数 / 槽）、能力（已安装的角色）、最后心跳 |
| 事件 / 候选 / 决定 | 与现有 `Trigger / Decision` 同构；来源是飞书、GitHub、邮件日程、定时 |
| 观察记录 | `would_accept` 决定 + 负责人标注（判断正确 / 不该接）→ 准确率 |
| 审计 | 事件 → 决定 → 任务 → 工单 → 命令摘要 → 凭据名；可按编号检索、导出 |
| 打扰 | 按人按天计数；预算 |

组织主管（headless Router）按 Super-agent 原型：Source → Trigger → Thread → Eval（准入 gate + 规则研判）→ 建任务 / 候选；回复回到原处（群 / PR 评论），≤100 词。

### 10.2 组织工作清单（Web 页面）

- 工作任务管理：建 / 改 / 取消、优先级、范围、负责人、截止、依赖、工作流模板。
- 工作任务列表：按范围 / 负责人 / 阶段 / 节点筛选；行 = 组织任务号 · 标题 · 阶段 · 负责人或节点 · 清单进度 · 需要人。
- 任务卡：与 TFA 的任务卡同构（§9.2），多「领取」「派单给…」「转交」。
- 领取 / 分配：人领取（范围允许名单内）；TFA 自动领取（范围接单模式为自动、节点在线、能力匹配）；负责人派单给人或节点（带授权：范围、能否改文件）。
- 范围与规则、观察记录（可标注）、节点注册表、审计、打扰预算。
- 视觉沿用 TFA 的 `DESIGN.md`（浅色纸栈、三种状态色、系统字体）。

### 10.3 节点协议（TFA ↔ 服务端）

```
POST /nodes/register        {nodeID, person, roles[], version}        → token
POST /nodes/heartbeat       {open tickets, slots, online}
GET  /tasks?scope=&mine=1   拉取：派给我的 / 我领的 / 待领取（本范围）
POST /tasks/{id}/claim      领取
PATCH /tasks/{id}           {stage, items:[{id,status,doneBy}], resultSummary}   上行
POST /tasks/{id}/needs      {kind: answer|review|blocked|failed, question}       上行
GET  /scopes/{id}/policy    规则与接单模式（带版本）                               下行
推送（WebSocket / 长轮询）：派单、打回 / 通过、规则版本变化
```

**同步规则**
- 下行：任务（字段、工作流、清单）、派单、规则版本。
- 上行：阶段、清单勾选、结果摘要、需要人、当天打扰次数。
- 只在本地：终端、worktree、工单细节、命令全文（审计只上传命令摘要和凭据名）。
- 离线：本地照常；重连后合并——任务字段以服务端为准，清单勾选取并集，同一项两边都改成不同状态 → 进「需要你」让人定。
- 节点对每个组织任务在本地也建一行 `task`（`origin / origin_id` 回指），工单只在本地。

## 11. 分期与验收

| 期 | 内容 | 完成标准 |
| --- | --- | --- |
| **1. 个人清单** | §3 模型 + §7 存储与迁移；§5 引擎（createTask / assign / itemDone / advance / approve / reject / cancel；report 映射）；§6 `tfa task`；§8 prompt；§9.1–9.4 界面；设置里可选工作流模板 | 单测覆盖：清单项全 done 推进阶段、assign 建工单并回指、report 各状态对清单项的映射、handback 变新任务、迁移。私有 tmux 上用假 agent 跑通：建任务 → 两项给开发（一张工单）一项给你 → 执行者 progress --item 勾一项、ready 勾另一项 → 你勾自己的 → 进待评审 → 通过 → 完成。主管说一句 → 清单里多一个待分配任务，不建工单 |

| **4. 看门狗** | 模型研判工单是否偏离清单项目标（输入：ack、progress、过程记录） | 偏离的工单 25 分钟内以 `--ask` 问到人 |

## 12. 不做

- 不做以对话为首屏的界面；主管终端只是辅助入口。
- 不做独立的「Agent 管理」页；Agent 只以角色和工单出现。
- 不同步终端、worktree、命令全文到服务端。
- 不给主管分配权：谁来做永远由人（或范围的自动接单规则）决定。
- 不引入 Thread 概念到个人层；个人层用任务的活动时间线。

## 13. 风险

| 风险 | 对策 |
| --- | --- |
| 清单项粒度和工单粒度打架（Agent 一口气把几项都做了） | `ready` 勾全部；`progress --item` 只是加分项，不强求 |
| 「你」做的项忘了勾，任务永远在进行中 | 清单页的「今天」视图把你名下 doing 超过 2 天的项提到前面；不弹窗 |
| 主管建议的清单项质量差 | 人在「谁来做」里能改文字、增删项；建议只是默认 |
| 迁移把现有工单打乱 | 迁移只读工单生成任务，不改工单；可随时重跑；先在备份库上跑一遍 |
| 组织端改变 TFA 定位（数据离开本机） | 第 3 期前单独做安全设计（凭据不上传、命令只传摘要、节点 token 可吊销） |
| 概念变多 | 人能看到的只有：任务、清单项、谁来做、工作流、需要你。工单、角色、规则留在第二层 |

## 14. 开放问题（开发前确认）

1. 任务编号：`A-<id>` 可以吗？还是和工单一样用 `#`，靠前缀「任务 / 工单」区分？
2. 个人层要不要「待领取」阶段？本文默认：个人建的任务直接进行中，只有组织任务才有待领取。
3. 打回时意见送给原工单（现有 `feedback`）还是新建一个清单项？本文默认：有工单就送工单，没有就新建项。
4. 候选自动接单时的默认角色：本文默认开发；规则可指定。
5. 第 1 期的「谁来做」是否允许「让主管定」（把分配交给主管研判）？本文默认不允许，保持人决定。
