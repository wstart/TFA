# 主管派发重设计：先定角色，再接单

> 状态：**第 1 期已实施**（工单 #4，2026-11-07）。
> 来源：人在主管终端里说「每次都要打开一次工单、启动一个线程，这个不合适」，随后要求「分为几个角色，根据任务先生成对应角色的 Agent，设计好它的主要行为，再进行接单」。
> 确认结果：先做「助理」+「开发」两个角色；主管先看现有角色再派单，**没有合适的角色就先和人对焦，再新建角色接单**；尽量不要一个需求开一个终端。实现与方案的差异见文末「实现说明」。

---

## 1. 现在的问题（11-07 主管会话里实际发生的）

| 现象 | 根因 |
|---|---|
| 「看一下现在推特有啥好玩的」被拒：`不能在家目录开工单`，人只好现建 `~/Desktop/twitter` | 只有一种执行者，按「改代码」设计：每单必须有项目目录 + worktree |
| 「看看帕丁森试镜新 007」是 #1 的追问，却新开 #2：新终端 + 新 worktree + 新 Claude Code，上下文从零开始 | 工单 = 终端 = worktree 绑死；主管 prompt 只在人写了 `#编号` 或说「刚才那个」时才 attach |
| 查资料的结果也进「待评审」，人还要点「通过 / 打回」 | ready 一律进 review，不区分有没有要合并的东西 |
| 查资料的 agent 也是全部放行、能改任何文件 | 所有工单共用一份执行者 prompt 和一套权限 |

## 2. 方案

**角色 = 一份 Agent 定义**：主要行为（prompt）+ 运行方式（常驻还是每单一个、在哪个目录、什么权限、怎么交付）。

派发顺序改成：主管判断任务属于哪个角色 → TFA 确保这个角色的 Agent 在（不在就按定义生成并启动）→ 把工单交给它。

### 推荐的角色（先 3 个）

| | 助理 | 开发 | 评审（第 2 期） |
|---|---|---|---|
| 接什么 | 查资料、问答、分析、总结、和项目无关的事；关于代码的问题（只读） | 要提交的改动：代码、配置、文档 | 开发报 ready 后自动接 |
| Agent 怎么来 | **常驻一个终端**：所有助理单排队进同一个会话，追问自带上下文 | 每单一个终端 + git worktree（并行改同一仓库互不干扰），即现状 | 每次在该工单的 worktree 里临时起一个，审完退出 |
| 目录 | `~/.tfa/agents/助理`，不需要项目目录；问到哪个项目就只读那个目录 | 工单 worktree | 工单 worktree |
| 权限 | 禁用 Edit / Write / NotebookEdit；Bash、WebSearch、WebFetch 放行 | 全部放行（现状） | 禁用编辑，只读 + 跑构建和测试 |
| 交付 | ready = 答案：主管一句话转告人，**工单自动结单，不进待评审** | ready → 待评审（通过 / 打回），即现状 | 通过 → 工单进待评审并附评审意见；有问题 → 自动打回开发一次，仍不过再交给人 |
| 主要行为 | 先给结论再给来源和时间；不改文件；发现要改东西就 `tfa handback`，由主管转成开发单 | 现在的执行者规则 | 只审不改；只报真实问题（附复现或证据）；不提风格偏好 |

### 派发流程

```
人 ──▶ 主管：判断角色（要提交改动 → 开发；否则 → 助理；拿不准 → 助理）
        │
        ├─ 助理单 ──▶ 进常驻「助理」终端的队列（空闲时送入，一次一张）
        │              └─ ready ──▶ 主管转告人 ──▶ 自动结单
        │              └─ 要改东西 ──▶ handback ──▶ 主管改派开发单
        │
        └─ 开发单 ──▶ 新 worktree + 新终端（现状）
                       └─ ready ──▶ [评审] ──▶ 待评审 ──▶ 通过 / 打回
追问：接着某个工单的结果问 → attach 到那个工单（不再新开）；
      新的问题 → 新助理单，但仍进同一个助理终端，不开新终端。
```

### 主管规则的变化

- 接单时多一步「选角色」：先 `tfa read roles`，再 `tfa route accept --role 助理|开发 …`。助理单不需要 `--dir`。
- 现有角色都不合适：先用两三句话和人对焦（名称、接什么、主要行为、常驻还是每单、能不能改文件、交付要不要评审，默认推荐常驻），人确认后 `tfa role set` 新建，再用它接单。
- 开发报 ready 后：现有角色里有「评审」，主管先派它核对（`--dir` 用该单的工作目录），评审交付后再把结果和评审结论一起告诉人；评审提了问题，问人要不要转回原工单修。
- 追问判断放宽：人的话明显接着最近某个工单的结果（例如结果里的某一条），就 attach，不用等人写 `#编号`。
- 其余不变：主管仍然不读代码、不改文件、不改写请求原文。

## 3. 改动点

| 层 | 改动 |
|---|---|
| `SuperagentCore/Model` | `Ticket` 加 `role`；新增角色定义（id、名称、常驻/每单、目录、权限、交付方式） |
| `SuperagentCore/Store` | `ticket` 表加 `role` 列，旧工单默认「开发」 |
| `SuperagentCore/Engine` | 助理单不要求目录、不建 worktree；助理 ready 自动结单；常驻 Agent 一次只跑一张单，其余排队；（第 2 期）开发 ready 入队评审 |
| `Mux/SuperagentRuntime` | 按角色启动：助理找 `@tfa_role=assistant` 的常驻终端，没有就建；新单复用现有的 deliver（空闲时打字 + 回显核验）送入 |
| `TFACLIKit` | `route accept --role`；常驻终端里 `tfa report` 等命令按「这个 Agent 当前的工单」定位（现在靠 `TFA_TICKET`，常驻终端会换单） |
| `SuperagentCore/Prompts` | 主管加选角色 + 追问规则；执行者 prompt 拆成助理 / 开发 / 评审三份 |
| 角色定义 | 存在 `superagent.db`（只存人改过的内置角色和新建的角色）；启动 Agent 前写出 `~/.tfa/superagent/role-<角色>.md` |
| 界面 | 常驻角色的终端归入侧栏「角色」分组；工单行显示角色；主管面板「角色」卡片可查看、编辑、新建、删除 |

## 4. 分期

| 期 | 内容 | 完成标准 |
|---|---|---|
| 1 ✅ | 助理 + 开发 + 主管选角色与追问规则 + 主管和人对焦后新建角色 | 单测覆盖角色分派、助理单自动结单、常驻 Agent 排队；私有 tmux 上用假 agent 跑通：两张助理单只建一个终端、一次一张、交付即结单、追问回到同一个终端 |
| 2 | 评审角色 | 一个开发单 ready 后自动评审，意见附在待评审里；打回只自动一次 |
| 3 | 人自定义角色（如「运维」「写作」） | 在面板新增一个角色并接到它的单 |

## 5. 取舍与风险

| 取舍 / 风险 | 处理 |
|---|---|
| 为什么不让主管每单现场生成一个定制角色 | 主管的规则是不改写请求、不写实现指示；现场生成的 prompt 无法测试，权限也不该由主管定。角色定义固定，主管只负责选。（如果你要的是现场生成，见待确认的问题） |
| 常驻助理是串行的：同时问两件事要排队 | 省终端和额度、追问带上下文。不够用再加「助理最多 N 个」 |
| 常驻会话上下文越来越长 | 依赖 Claude Code 自动压缩；退出或卡住时 TFA 按现有对账逻辑重启它 |
| 助理的「只读」不是物理隔离：Bash 仍能写文件 | 禁用编辑工具 + prompt 约束。主管能做到物理隔离是因为它只需要 `tfa`；助理要跑 curl、搜索，离不开 Bash |
| 放松了原设计「一个工单一个会话」 | 只对助理放松为「一个 Agent 串行处理多张单」；工单状态仍然各自独立，不跟随会话 |
| #3 正在改侧栏左上角 | 这次没改 `SidebarView`；常驻终端靠分组出现在侧栏 |

## 实现说明（与方案的差异）

| 方案 | 实现 | 原因 |
|---|---|---|
| 角色定义放 `~/.tfa/roles/<角色>.md` | 放在 `superagent.db`，经引擎写入；prompt 文件在启动 Agent 前生成 | 唯一的事实来源仍是数据库；主管用 `tfa role set` 新建角色时和其他写入走同一条路 |
| 侧栏固定一行「助理」 | 常驻终端自动归入「角色」分组 | 不和 #3 的侧栏改动冲突；没有新增界面概念 |
| 只有内置角色 | 主管和人对焦后可 `tfa role set` 新建（默认常驻、只读、直接交付）；内置角色只能由人在面板里改「接什么」和主要行为 | 人确认时追加的要求 |
| `--role` 必填 | 不写 `--role` 按「开发」接（旧用法）；在家目录不写 `--role` 时，报错里提示 `--role 助理` | 定时任务、退回、旧提示都还能用；主管 prompt 要求每次都写 |
| 常驻终端里靠 `TFA_TICKET` 定位工单 | 常驻终端设 `TFA_AGENT=<角色>`，每条消息开头写工单号，命令写 `--ticket <id>`；没写时取它正在做的那一张（恰好一张才算） | 一个终端会先后处理多张单 |
| 评审由 TFA 在开发 ready 后自动发起（第 2 期） | 先由主管规则发起：有「评审」角色就先派它核对，再告诉人；「评审」是主管和人对焦后新建的常驻、只读、直接交付角色 | 人在试用时要求「开发交付先经评审再给人」；写进主管 prompt，主管重启也不会忘。自动发起和「打回只自动一次」仍属第 2 期 |
| 停止工单就中断终端 | 常驻角色只在它正在做这张单时才中断 | 不打断它手上的别的单 |
